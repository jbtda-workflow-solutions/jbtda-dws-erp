# Agent Instructions & Execution Constraints

This file is the root agent operating manual for the JBTDA-DWS-ERP repository.
All AI agents working in this codebase MUST read and follow these rules before
writing any code.

## Zero-Memory Protocol

**Never assume context from a previous chat session.** The sole source of truth
is the code and documentation committed to this repository. Begin every session
by reading:

1. `AGENT_SPECIFICATION.md` — master spec and architecture
2. `docs/ARCHITECTURE.md` — topology and service boundaries
3. `docs/DATABASE_SCHEMA.md` — current Prisma schema and migration log
4. `docs/SECURITY.md` — auth mechanics and RBAC rules
5. `docs/CHANGELOG.md` — latest changes

## Mandatory Rules

1. **Documentation first:** Document architectural decisions and data model
   changes in `/docs` before or immediately upon implementation.
2. **Changelog entries:** Every route, migration, dependency, or schema change
   must append an entry to `docs/CHANGELOG.md`.
3. **Multi-tenancy:** Every business-domain query must include
   `where: { organizationId: request.organizationId }`.
4. **Integer money:** Store all monetary values as `BIGINT` cents. Never use
   `FLOAT`, `DOUBLE`, or `REAL`.
5. **No AI in production:** The built application must be 100% deterministic
   TypeScript. No runtime LLM API calls.
6. **Prisma migrations:** Use `prisma migrate dev` locally;
   `prisma migrate deploy` in CI/CD. Never edit migration SQL by hand.
7. **snake_case PostgreSQL:** All column and table names use `snake_case` as
   generated by Prisma's default mapping.
8. **Containerization & Deployment (Unified Monolith):** The application MUST be
   built using a single root `Dockerfile` that utilizes a multi-stage build. The
   build must compile the React frontend, compile the Fastify backend, and package
   them together into a single runtime image. Fastify serves the frontend assets
   via `@fastify/static`. Do not provision separate frontend hosting.
9. **File Tree & Pre-Modification Verification:** Agents MUST review the complete
   file structure below before creating, modifying, or moving files to prevent
   duplicating files across directories. Whenever files are added, removed, or
   moved, the agent MUST update this `Directory Layout` section in `AGENTS.md`
   and append an entry to `docs/CHANGELOG.md` to keep the source of truth accurate.
10. **No Autonomous Git Commits (Provide Commit Messages):** Never run
    `git commit` or `git push` on behalf of the user. The user manages git
    staging, commits, and pushes manually. At the conclusion of any task or
    revision where a commit would typically occur, the agent MUST provide a
    ready-to-use, conventional git commit message summarizing the changes made.
11. **Local Type Verification Allowed / No Runtime Execution:**
    Agents MAY run `npm install --cache /tmp/.npm-cache`, `npx prisma generate`,
    and non-emitting typecheck commands (`npm run typecheck`, `tsc --noEmit`, or
    `npm run build`) solely to verify TypeScript types and prevent compiler breaks
    before concluding tasks.
    Agents MUST NOT run `npm run dev`, start background dev servers, or execute
    runtime application code on the host machine. The development machine is not
    used to run, demo, or execute the project. Production builds, runtime execution,
    and database migrations remain strictly handled by Cloud Build / Docker during
    deployment to Cloud Run. All new dependencies must still be declared directly in
    `package.json` manifests.
12. **Clean Imports & Compiler Tolerance:** Frontend builds use `tsc && vite build`.
    Never leave unused icon imports or variables in files. `frontend/tsconfig.json`
    has `noUnusedLocals: false` and `noUnusedParameters: false` configured as an
    operational tolerance safeguard against transient Docker build breaks, but
    agents must always keep imports clean and prune unused symbols.
13. **Module-Gate Review Protocol:** Development proceeds one module at a time per
    `docs/STAGES_ROADMAP.md`. When a module is completed, the agent MUST mark its
    checklist items `[x]` in `docs/STAGES_ROADMAP.md`, synchronize `AGENTS.md` and
    `docs/CHANGELOG.md`, provide a ready-to-use conventional git commit message,
    and STOP for user review before beginning the next module.

## Cloud Run Runtime Configuration (Variables & Secrets)

The application relies strictly on Google Cloud Run container configuration (zero `.env` files in production).

### 1. Cloud SQL Connections (Cloud Run UI)
- Attached Instance: `PROJECT_ID:REGION:INSTANCE_NAME` (e.g. `digitalworkflowsolutions-erp:us-central1:erp`).
- Cloud Run automatically mounts the Unix socket into `/cloudsql/<INSTANCE_CONNECTION_NAME>`. The Prisma plugin auto-discovers this path.

### 2. Environment Variables (Cloud Run UI)
| Variable | Description / Purpose |
| :--- | :--- |
| `INSTANCE_CONNECTION_NAME` | Cloud SQL instance connection name (e.g. `PROJECT_ID:REGION:INSTANCE_NAME`). Explicitly defines the Cloud SQL Unix socket target (`/cloudsql/<INSTANCE_CONNECTION_NAME>`). Required for multi-tenant isolation and portable tenant/client forks. |
| `GOOGLE_CLIENT_ID` | Google OAuth 2.0 Web Client ID (used for token verification & served to frontend via `/api/v1/auth/config`) |
| `DB_USER` | PostgreSQL database user (e.g. `erp_admin`) |
| `DB_NAME` | PostgreSQL database name (e.g. `erp`) |
| `FRONTEND_ORIGIN` | Allowed origin for CORS (e.g. preview deployment URL or `http://localhost:5173`) |
| `NODE_ENV` | Set to `production` |

### 3. Secrets Exposed as Environment Variables (Secret Manager)
| Secret in Secret Manager | Mounted Variable | Purpose |
| :--- | :--- | :--- |
| `user_erp_admin_pass...` | `DB_PASSWORD` | PostgreSQL user password |
| `erp_session_secret` | `SESSION_SECRET` | 32+ character random secret for signing and encrypting session cookies |
| `erp_webhook_secret` *(Stage 2)* | `WEBHOOK_SECRET` | 64-character secret for n8n asynchronous webhooks |
